# GPU sampling follow-up, 2026-10-26

No production changes or new GPU calls were made for this audit. The V14 buffer-capacity experiment remains rejected and archived at `dist/nvml-v14-prototype`.

## Reject preflight gating under current semantics

`resources.ts:719–741` reads the source before attribution. It then memoizes NVIDIA file enumeration once per PID within that sample. Positive GPU holders stay in `Sampler.held` while PID/start identity remains; that is deliberately more permissive than requiring an open device descriptor at every subsequent sample. Foreign/stale PID handling and namespace fallback live in `gpu.ts:60–149`. Sample-only processes can be attributed even before the driver's process list includes them (`gpu.ts:115–118`).

A conservative preflight must retain every already-held matching PID, probe every other owned PID, and use the same per-sample opened-file map for subsequent attribution. Null/partial enumeration cannot safely prove no interest. Keeping global memory/utilization queries preserves device figures, but skipping per-process queries is still not equivalent.

The decisive issue is sample history. `gpu_nvidia.ts:164–195` advances the per-device `seen` watermark only from fetched valid samples. Suppose a workspace PID uses the GPU briefly, closes its FD before a resource sample, then reopens it later. Baseline reads consume the earlier sample and advance `seen` even if current holder checks prevent attribution. A preflight gate that sees no open FD skips that read; the later first positive preflight can fetch and average the earlier interval too. The same issue applies when only foreign clients produced prior samples. Inventing a wall-clock cutoff, resetting the watermark, or fetching/discarding the first active batch changes history or drops the first active sample. The NVML count query does not supply the newest sample timestamp.

The gate also adds O(P + sum FDs) work: one descriptor-directory read and one readlink per descriptor for every unremembered workspace PID, each resource sample. The V14 trace had33 owned processes per resource sample and no GPU FD enumeration in the ordinary empty trusted-list case. Those probes would all be additional work. The measured old utilization data call cost is about3ms/device on this idle driver, or about0.3CPU percentage points at two devices and0.5Hz before new scans. That is an estimate from the isolated experiment, not a measured gating saving. A new state machine to preserve this history is not justified.

## Newer NVML API: available, no demonstrated cheaper path

The installed library is `/usr/lib/x86_64-linux-gnu/libnvidia-ml.so.560.35.03` (SHA256 `660081fa0dfaa772c8dd11ca90e6d326273bd84813e2d809024352e308e35334`); `/proc/driver/nvidia/version` reports560.35.03. Its exported symbols include both `nvmlDeviceGetProcessUtilization` and `nvmlDeviceGetProcessesUtilizationInfo`. This was checked by reading ELF symbols, without initializing NVML. The CUDA header `/usr/local/cuda/include/nvml.h` (SHA256 `2ec2431ac69cf205ecf6cd2bf24d0402997975505d574cee5aec6a85a4c520c9`) declares the new API, while `/usr/include/nvml.h` is older and lacks it.

The newer interface wraps version/count/timestamp/array pointer in one structure and adds JPEG/OFA fields. It still requests samples newer than a prior returned CPU timestamp, reports required capacity on insufficient size, and can return NOT_FOUND. It does not document a cheaper empty-list query or an independent newest-timestamp read. [NVIDIA API documentation](https://docs.nvidia.com/deploy/nvml-api/latest/api/group__nvmlDeviceQueries.html), [structure documentation](https://docs.nvidia.com/deploy/nvml-api/latest/api/structnvmlProcessesUtilizationInfo__v1__t.html).

On this Linux x64 ABI, the header implies a24-byte request structure (u32 version/count, u64 last timestamp, pointer) and40-byte samples (u64 timestamp followed by seven u32 fields, padded to8-byte alignment). These are distinct from the old32-byte sample. A diagnostic prototype would need exact layout checks, the same timestamp filter/SM validation/averaging, and API failure fallback. Static disassembly shows distinct entry wrappers but cannot establish driver work or output equivalence. No speedup is claimed. Given the rejected capacity-reuse results and unchanged documented history contract, keep the existing product path unless a small later isolated old/new API experiment proves a benefit; do not introduce a gating state machine or lower sampling cadence.
